# LICENSE_POLICY.md

Saved 2026-11-10 (owner directive PART A). This is a WORKING POLICY, not legal advice; a lawyer reviews it when budget allows.

## Scope

Applies to the WHOLE project and every future milestone (M1 through M7d). Every third-party piece is covered: Rust crates in the compiler, runtime and tools; vendored code; bound C/C++ libraries; JavaScript or Python packages in tools; fonts, icons, images, datasets, sample assets; and any code copied from the web, Q&A sites or blogs. Code copied from the web, Q&A sites or blogs is never allowed unless the license is allowed by this policy and recorded in THIRD_PARTY.json like any other third-party piece.

## Rules

- Only open-source libraries. Open source means OSI-approved licenses or recognized public-domain dedications (CC0, Unlicense). No license file = not allowed.
- Dual-licensed: pick the allowed option and record the choice in THIRD_PARTY.json.

## Tier A - ALLOWED, no notice required in distributed binaries (verify by reading the license text)

- Public domain
- CC0
- Unlicense
- 0BSD
- MIT-0
- zlib
- Boost-1.0

## Tier B - ALLOWED, notice must ship

- MIT
- BSD-2-Clause
- BSD-3-Clause
- ISC
- Apache-2.0 (also with the LLVM-exception)

## DENIED

GPL, LGPL, AGPL, MPL, EPL, CC-BY-NC, BSL, SSPL, Commons Clause, "free for non-commercial" offers, any custom or source-available license, any license that restricts commercial use, and unknown licenses (including any license not listed in a tier above and not clearly public domain).

## Selection order

1. The license is allowed.
2. Pick the technically BEST option (maturity, speed, security record, maintenance activity, quality of the C API, Windows/Linux/Android support).
3. If two options are comparable, prefer Tier A over Tier B.
4. NEVER choose a weaker library only for a nicer license.
5. Record at least two alternatives compared, and why the winner won, in THIRD_PARTY.json.

Dev-only and build-only tools that are not shipped or linked must also be open source, and are marked "dev-only" (or "build-only") in THIRD_PARTY.json.

Licenses can change between versions: re-check on every version bump. If a dependency moves to a denied license, pin the last allowed version, flag it in LYKAON_DEVIATIONS.md (append only), and plan a replacement.

## Records

- THIRD_PARTY.json (machine-readable): name, version, source URL, pinned commit or hash, SPDX id, license file path, tier (A or B), notice required in binary (yes, no or verify), dual-license choice, how it is used (linked, vendored, bound, build-only, dev-only), date checked, reason chosen and alternatives compared.
- third_party_licenses/<name>-<version>/ holds the full LICENSE and NOTICE files copied from upstream.
- LICENSES/<SPDX-id>.txt holds each license text once.
- THIRD_PARTY_LICENSES is the human-readable file GENERATED from THIRD_PARTY.json; it is regenerated by the check and never edited by hand.

## Tool and gate

tools/license_check (deny.toml for the cargo-deny license allowlist, checked by a script that works without cargo-deny installed too; cargo-about or cargo-license may generate the human-readable list for Rust when available). It fails on:

- unknown or denied license,
- a dependency missing from THIRD_PARTY.json,
- a missing license file,
- a license that changed since the last check (the SPDX id recorded in THIRD_PARTY.json no longer matches the metadata).

Run it in CI and before every release. NO new dependency (Cargo.toml entry, vendoring, package, binding, font, icon, dataset, asset) may be added without a THIRD_PARTY.json entry and a passing check.

cargo-deny itself is a dev-only external tool (not a project dependency, never shipped).

## Release rule

The license check must pass before every release, and THIRD_PARTY_LICENSES plus third_party_licenses/ ship with every release (RELEASE_PLAN.md, 0.1.0-alpha.1 criteria).
